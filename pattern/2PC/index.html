Overview

This diagram illustrates the Two-Phase Commit (2PC) protocol implemented in a distributed system for e-commerce transactions.

The 2PC protocol ensures that all participating services either commit or roll back a distributed transaction atomically, maintaining consistency in a distributed environment.

Architecture Components

  • Order Service (Coordinator): Orchestrates the 2PC workflow and coordinates participants
  • Payment Service (Participant): Handles payment validation and fund locking
  • Inventory Service (Participant): Manages stock checking and inventory reservation
Phase 1: Prepare Phase
Step 1: Client sends order placement request containing user information, product details, amount, and quantity.
Step 2: Order Service generates a Global Transaction ID (G-TID) for this transaction.
Step 3: Order Service creates an initial order record with PENDING status.
Step 4: Order Service sends a Prepare request to Payment Service in parallel with Inventory Service.
Step 5: Payment Service checks user balance and locks funds, creating a PREPARED transaction.
Step 6: Inventory Service checks product stock and reserves items, creating a PREPARED transaction.
Step 7: Both participants respond with success or failure status.
Phase 2: Decision Phase
Step 8: Order Service evaluates the responses from participants.
Step 9: If all participants succeed, Order Service proceeds to commit phase.
Step 10: Order Service sends Commit requests to both Payment and Inventory services.
Step 11: Payment Service updates transaction status to COMMITTED and releases held funds.
Step 12: Inventory Service updates transaction status to COMMITTED and decreases stock.
Step 13: Order Service updates the order status to PAID.
Step 14: Success response sent to client.
Step 15: If any participant fails, Order Service initiates rollback.
Step 16: Order Service sends Rollback requests to both Payment and Inventory services.
Step 17: Payment Service updates transaction status to ABORTED and releases held funds.
Step 18: Inventory Service updates transaction status to ABORTED and releases reserved stock.
Step 19: Order Service updates the order status to FAILED.
Step 20: Failure response sent to client.

Key Features of This Implementation

  • Distributed Transaction Coordination: Maintains atomicity across distributed services
  • Fault Tolerance: Robust rollback mechanism when participants fail
  • Concurrency Control: Proper row-level locking to prevent race conditions
  • Idempotency: Operations designed to safely retry in case of network issues
  • Error Handling: Graceful fallbacks in case of participant failures
